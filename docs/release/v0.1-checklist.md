# PicViewMac v0.1 release checklist

Three states only:

- **PASS** — verified automatically in this repository, with the command recorded.
- **MANUAL-PENDING** — needs a human at a display; never marked PASS until someone does it.
- **FAIL** — a check that ran and did not pass. (Currently none.)

Verification record: `docs/release/v0.1-rc1-automated-verification.md`.
Artifact verification: `scripts/verify-release.sh`.

## 3. MANUAL-PENDING

These need a human in front of a display. They are **not** verified, and no
automated result above should be read as covering them.

| # | Item | Why it cannot be automated here | What to do |
| --- | --- | --- | --- |
| M1 | Mission Control behavior with 1, 2 and 3 viewers | Requires the Mission Control UI | Enter Mission Control, confirm each viewer appears as its own window |
| M2 | Stage Manager behavior | Requires the Stage Manager UI | Move a viewer into a stage and back |
| M3 | Native tiling / window snapping including its animation | Requires interactive dragging | Drag a viewer to a screen edge and onto another window |
| M4 | Third-party window managers (Rectangle, yabai, AeroSpace, Amethyst — whichever the tester has) | Requires their interactive UI | Snap, move and resize a viewer; record observed behavior |
| M5 | Native Full Screen transition (Space animation, menu bar behavior) | The command, eligibility and state independence are verified; the transition needs a display | Toggle full screen with ⌃⌘F and the green button; confirm no phantom windows |
| M6 | Liquid Glass / material visual quality | Screen capture is unavailable to the automated environment | Compare chrome surfaces on macOS 26+ against the macOS 14–15 path |
| M7 | Hover feel and timing (150/250/300 ms, idle fade) | Timing values are asserted; subjective feel is not | Hover the edges and the top region, judge whether it feels right |
| M8 | Light/Dark and Reduce Transparency / Reduce Motion, visually | Policies are verified on both branches; the rendering is not | Toggle each system setting and look at the chrome |
| M9 | Visual comparison against reference viewers (for example Picview or Pixea) | Judging similarity is a human call | Open the same folder in each and compare |
| M10 | Instruments profiling (peak decoded memory, main-thread stalls) | No Instruments harness in the automated environment; only an RSS trend is recorded | `xcrun xctrace record --template 'Time Profiler' …` |

## 5. Tagging policy

`v0.1.0-rc1` may be tagged while §3 is pending, because a release candidate exists
precisely to gather that manual verification. The RC2 fixes add the §4 group, so
`v0.1.0` must not be tagged until every row in **§3 and §4** has been performed and
recorded:

```bash
# only after §3 is complete
git tag -a v0.1.0 -m "PicViewMac v0.1.0"
```

## 6. Naming residue

The shipped, user-visible name is now **PicLight**: bundle name, display name,
executable name, menu title, `PicLight.app`, `PicLight-<version>.dmg` and the DMG
volume name.

Still carrying the old `PicViewMac` name on purpose, because renaming them is an
invasive refactor rather than a user-visible fix:

| Item | Where |
| --- | --- |
| SwiftPM product and target names | `Package.swift` |
| Source directory names | `PicViewMac/`, `PicViewMacTests/` |
| Xcode scheme | `PicViewMac` (auto-generated from the package) |
| Bundle identifier | `com.example.picviewmac` in `scripts/build-release.sh`; changing it would also move the `UserDefaults` domain |
| Test invocation examples | `xcodebuild -scheme PicViewMac ...` throughout the docs |

Renaming the bundle identifier is a user-affecting change (saved settings live
under it), so it should be a deliberate decision rather than a cleanup.

## 7. Explicitly out of v0.1 scope

No slideshow, permanent editing, rename/move, clipboard editing, always-on-top,
custom tabs, updater, telemetry, cloud/network features, RAW/pro formats,
HDR/EDR, J3 customizable toolbar, persistent disk thumbnail cache, or
signed/notarized distribution. HEIC/HEIF remains outside the v0.1 claim.
