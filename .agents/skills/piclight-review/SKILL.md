# PicLight 改动评审

从[当前项目约定](../../../AGENTS.md)和用户要求判断行为；[验证指南](../../../docs/testing.md)帮助核对证据。评审的是具体差异和相关调用，不是旧文档里的通过数量。

## 检查重点

| 改动面 | 需要追踪 |
| --- | --- |
| 标题栏、工具坞或侧栏 | 画布范围、手动视口、第一帧、反复切换和原生控件是否符合当前行为 |
| 手势与焦点 | 覆盖层转发、隐藏视图命中、看图/网格分流，以及控件编辑焦点 |
| 扫描、解码和缓存 | 文件身份、请求代际、迟到发布、取消和资源结束；既检查生产端也检查使用端 |
| 设置或文件操作 | 持久化、生效与刷新、取消/失败结果，以及真实系统写入的触发点 |
| 测试与交付 | 是否能捕获原来的错误、恢复资源和设置；证据是否属于实际工作版本或交付包 |
| 文档与规则 | 名称、命令和路径对照源码；技能是否只在合适任务触发，未完成方案是否明确标记 |

例如测试“标题栏显隐后窗口大小一样”，仍可能漏掉画布高度改变。评审还要检查图片位置、缩放和中心，而不是据窗口断言直接认定使用问题已修复。

## 给出结论

缺陷写清具体位置、触发条件、用户影响和证据，优先报告行为错误与生命周期问题。建议改进与必须修复分开；没有问题可以直接说明，不为凑条目提出风格意见。

接收反馈时先用当前源码和实际行为核对，再修复或解释。长期决策可以作为理由，不能代替当前证据。按[记录规则](../../notes/README.md)更新相应决定，无需为每条局部意见建新文档。

评审不会自动授权新 agent、真实格式关联、安装、提交或发布。需要独立评估时遵循当前任务与工具的授权规则。
